01 / The problem

A parking count only helps when it changes what happens next.

We wanted the model to do more than detect a car. It needed to show which bays were free, prevent a new arrival when all three were occupied, and still let a parked vehicle leave. A browser view then connected those physical events to a readable current state.

A university team prototype — an exploration of sensing and feedback, not a commercial installation.

from sensor to story.

On the prototype, board readings travel over USB serial to a laptop bridge, then pass through a receiver and database before the browser presents the parking state.

Illustrative signal path · no network or device activity on this pageOne-second recording was a target while the full chain is active.
Hardware sensing

Three bay sensors and two lane sensors inform local occupancy and gate decisions.

Data transport

A Python bridge reads the Arduino's USB serial stream and forwards structured readings.

Server-side saving

A PHP receiver is the hand-off point for validating and saving records to MySQL.

Stored history

Records can support an occupancy-history view; saved history is distinct from current state.

Browser presentation

The dashboard surfaces available spaces, bay states and arrival/departure activity.

Operational condition

The one-second target depends on the board, bridge and server all being active; disconnection interrupts logging.

07 / Testing & lessons

What we know.
What remains open.

We separate reported working behaviour from evidence that still needs to be collected. The interactive page is a model of intended logic—not a test report.

Reported working in the project

  • Hardware sensing and live-data operation were reported working.
  • The final controller is Arduino UNO; the LCD was removed from the final build.
  • My assigned contribution was the dashboard and its connection to hardware data.

Awaiting final evidence

  • Confirmation that saved occupancy history renders end-to-end in the final dashboard.
  • Repeatable test records for full-capacity denial and independent exit behaviour.
  • Photos, demo footage and measured results have not been supplied here.
LESSON 01Serial ports are shared resources.

One process needs to own the board connection; a second reader can make the data path appear silent.

LESSON 02A web UI is another system boundary.

Hardware readings need a bridge, a receiver and clear handling before they become browser state.

LESSON 03Now is not the same as history.

A live occupancy value can look correct while saving, timestamps or historical rendering still need checking.
